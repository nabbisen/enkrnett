# 14. Verification plan

How the 241 requirements are verified, where each kind of test lives, and what a test must say.
This is the test design at the level of the specification (project rule: design specifications
are the source for test design). Concrete test cases are written per milestone in the handoffs,
from this chapter and the requirement tables, before the code they test.

## 14.1 Rules

| # | Rule |
|---|---|
| 1 | Every test names the requirement identifiers it verifies, in its name or its first line. A requirement with verification "Test" is met only when at least one test names it and passes. |
| 2 | Tests are derived from this book, not from the code. A test that can pass only because of how the code happens to be written is a defect of the test. |
| 3 | A requirement verified by "Inspection" or "Review" has a checklist line in the release checklist (chapter 11 §6) or in the milestone's acceptance checklist, with the evidence to record. |
| 4 | A requirement verified by a measurement (M-n) is met when the measurement's report records the value and the owner has accepted the report. |
| 5 | Rust tests live beside the module they test, in a separate file (`src/<mod>/tests.rs`), never inside the implementation file. Integration tests that need the platform run on the virtual machines. |
| 6 | A test that cannot run in CI (needs a radio, a device, or a person) is listed in the milestone handoff with who runs it and how its result is recorded. |

## 14.2 Test suites

| Suite | Runs | Where it lives | What it covers | Chapters |
|---|---|---|---|---|
| **Model unit tests** | CI, every push | `crates/enkrnett-model/src/**/tests.rs` | Settings validation (names in bytes and NFC, modes, limits), the UCI translation as pure functions, the pending-marker and snapshot formats, format versions | 6, 4 (password rules), 9 (error codes) |
| **Daemon unit tests** | CI | `crates/enkrnettd/src/**/tests.rs` | HTTP parsing and limits, routing and method rules, headers, session store, login delay, monotonic durations, JSON strictness, log-line content | 3, 4, 9 |
| **ubus client tests** | CI | `crates/enkrnett-ubus/src/**/tests.rs` | Message encoding against recorded `ubusd` exchanges | 6 |
| **API contract tests** | CI | `tests/api/` against the daemon on the x86-64 VM and against the mock | Every resource in every state, every shape, every error code, the greeting's exact fields, the authorization matrix, confirmation by join (simulated station disconnect), retried save | 4, 9 |
| **Browser harness** | CI (GitHub Actions: iOS Simulator, Android emulator) | `tests/browser/` against the mock daemon | Every screen in both languages at 360 and 430 px, the word check, storage blocked, the "not connected" path, countdown from `*_in`, QR rendering, accessibility audit, bundle size | 10, 3 (ENK-MGMT-003), 8 (ENK-FOOT-002, 011) |
| **VM integration** | CI nightly and before release; `tests/vm/` | x86-64 VM with simulated radios (M-6 material); malta VM for MIPS binaries | Transactions end to end: apply, health check, undo on failure, undo after restart with marker, drift; read-backs of chapter 2 (M-8 rows); DHCP per network; listener binding; OWE association on simulated radios; separation rows that need no real radio | 2, 6, 7 |
| **Device tests** | Before release, on each Tier 1 device; results in the release notes | `tests/device/` (checklists and scripts), run by whoever holds the device | Separation from real clients (M-8 part 2), OWE and Transition Mode with the client matrix (M-4), footprint and memory on the device (M-3), update from the previous release with settings kept, failsafe and button behaviour | 2, 5, 7, 8, 11 |
| **Usability test** | Before 0.3.0 and before 1.0.0 | Procedure in the M-7 handoff; results in `docs/src/measurements/` | Install, set up, change, update, erase with the guides alone; wording changes | 4, 5, 10 |
| **Build checks** | CI | Workflow files; `openwrt/lock/` | Budgets (ENK-FOOT-001 to 003), double build and comparison, lock completeness, word check, patch headers | 8, 11 |
| **Release checklist** | Each release | Chapter 11 §6 | Inspections and reviews: threat model current, docs match, legal basis, signatures, source offer | 11, 12 |

## 14.3 Verification method to suite

| Method in the requirement tables | Suite |
|---|---|
| Test (daemon behaviour, API, sessions, limits) | Daemon unit tests; API contract tests |
| Test (validation, names, formats) | Model unit tests |
| Test (transactions, read-backs, DHCP, binding, drift) | VM integration |
| Test from a client, port scan, M-8 | VM integration where no real radio is needed; device tests otherwise |
| Test per device profile; M-4; M-3 part 2 | Device tests |
| Browser harness; test with storage blocked; print to PDF | Browser harness |
| Schema test | API contract tests and browser harness, from one JSON Schema generated by `enkrnett-model` |
| CI, every build; CI configuration | Build checks |
| Inspection; Review; Release checklist | Release checklist, with the evidence named |
| M-1, M-7; usability test | Owner-run procedures; results recorded as measurement reports |

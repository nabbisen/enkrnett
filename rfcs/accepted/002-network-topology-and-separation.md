# RFC 002 — Network topology and separation

**Status.** Accepted (2026-09-29)
**Tracks.** How the device is connected, which networks it offers, and what may talk to what.
Startup decisions D-03 and D-04.
**Touches.** Firmware defaults (network, firewall, wireless, services); the daemon's
configuration model; status shown in the management UI; operator guides.

Terms are defined in [RFC 001](./001-scope-people-vocabulary.md).

## Summary

The device is a **routed access point**. Guests get their own network and reach the Internet and
nothing else. The operator manages the device through a separate **management network**. No
guest-facing interface accepts management traffic or platform administration.

```text
   Internet
      │
   Site router ───── site network ───── business devices
      │
    uplink
      │
 ┌────┴─────────────────────────────────────┐
 │ Device                                   │
 │   guest network       → Internet only    │
 │   management network  → manage the device│
 └──────────────────────────────────────────┘
```

## Motivation

| Fact | Source |
|---|---|
| A bridging access point places guests in the operator's own network. The operator this project serves cannot segment that network. | Analysis |
| Japan's regulator tells public Wi-Fi providers not to offer guest Wi-Fi on the business network, to separate the two, and to prohibit communication between guest devices. Its own example is a hotel whose guests could read files on the office copier. | [MIC guideline][mic], §3-3, §4-3 |
| Research on client isolation found every tested router vulnerable to at least one bypass. What blocked the attacks on OpenWrt was placing guest and main networks on separate bridges. | [AirSnitch][airsnitch], NDSS 2026 |
| On stock OpenWrt `root` has an empty password, SSH listens on all interfaces, and failsafe mode gives a root shell to anyone who presses a button during boot. | OpenWrt source: [`shadow`][shadow], [`dropbear.config`][dropbear], [`image-config.in`][failsafe] |
| OWE does not authenticate the access point and does not isolate clients. | [RFC 8110][rfc8110] §7 |
| The packages needed for routing and firewalling are already part of OpenWrt's default image, including on 8 MB devices. | [25.12.5 manifest][manifest] |

## Design

### 1. Networks

| Network | Medium | Wi-Fi security | Addresses | Exists when |
|---|---|---|---|---|
| Uplink | Ethernet | — | IPv4 by DHCP from the site router | Always |
| Guest | Wi-Fi | OWE, or OWE with Transition Mode | Own IPv4 subnet, served by the device | State `CLAIMED` |
| Management | Wi-Fi | WPA2-Personal and WPA3-Personal, with a key generated by the device | Own IPv4 subnet, served by the device | States `PENDING` and `CLAIMED` |
| Setup | Wi-Fi | OWE with Transition Mode | Own IPv4 subnet, served by the device | State `SETUP` |

States are defined in RFC 004. The guest network's OWE policy and the network names are
specified in later RFCs.

### 2. What may reach what

✓ allowed · ✗ denied

| From ↓ To → | Management UI and API | DHCP and DNS on the device | Internet | Site network | Guest clients | Management clients |
|---|---|---|---|---|---|---|
| **Guest client** | ✗ | ✓ | ✓ | ✗ | ✗ | ✗ |
| **Management client** | ✓ | ✓ | ✓ | ✗ | ✗ | ✗ |
| **Setup client** | ✓ | ✓ | ✗ | ✗ | — | — |
| **Uplink side** | ✗ | ✗ | — | — | ✗ | ✗ |

| Choice | Reason |
|---|---|
| Management clients reach the Internet | A phone on a Wi-Fi network without Internet may send its traffic through mobile data instead ([Android][android-default]). With Internet present, the phone stays on the management network. |
| Management clients do not reach the site network | A leaked management key must not open the operator's business network. |
| Setup clients do not reach the Internet | An unclaimed device must not give Internet access to whoever is in range. |
| The uplink side reaches nothing | The site network may contain hostile devices. |

### 3. Services reachable on the device

| Network | Reachable services |
|---|---|
| Guest | DHCP, DNS |
| Management | DHCP, DNS, management UI and API |
| Setup | DHCP, DNS, management UI and API |
| Uplink | None |

Anything else that answers is a defect.

### 4. Requirements

#### Topology

| ID | Requirement | Verification |
|---|---|---|
| ENK-TOPO-001 | The device shall route between its Wi-Fi networks and the uplink, translating addresses. It shall not bridge a Wi-Fi network to the uplink. | Inspection; test |
| ENK-TOPO-002 | The device shall obtain its uplink address by DHCP and shall require no change on the site router. | Test behind three different consumer routers |
| ENK-TOPO-003 | The device shall choose subnets for its Wi-Fi networks that do not overlap the uplink's subnet, and shall choose again by itself when the uplink's subnet changes. | Test with a colliding uplink subnet |
| ENK-TOPO-004 | The device shall accept the uplink on the Ethernet port named by the device profile. Every other Ethernet port shall carry no network. | Test per device profile |
| ENK-TOPO-005 | Where the hardware reports link state per port, the device should detect a cable in a port that is not the uplink port and tell the operator. | Test per device profile |

#### Isolation

| ID | Requirement | Verification |
|---|---|---|
| ENK-ISO-001 | A guest client shall not be able to open a connection to any address in the site network, in any private, link-local, shared, or unique-local range, or in the uplink's own subnet. | Test from a guest client |
| ENK-ISO-002 | The device shall not forward traffic between guest clients: within one BSS, between BSSes, between radios, and at IP level. | Test from two guest clients in each combination |
| ENK-ISO-003 | A guest client shall reach no service on the device other than DHCP and DNS. | Port scan from a guest client |
| ENK-ISO-004 | A management client shall not be able to open a connection to the site network, to a guest client, or to another management client. | Test from a management client |
| ENK-ISO-005 | The device shall accept no connection from the uplink side. | Port scan from the site network |
| ENK-ISO-006 | Guest and management networks shall be separate bridges. | Inspection |

#### Exposure

| ID | Requirement | Verification |
|---|---|---|
| ENK-NET-008 | The device shall offer IPv4 only on its Wi-Fi networks, and shall drop IPv6 that arrives on them or would be forwarded for them. | Test with an IPv6-enabled client |
| ENK-NET-009 | The device shall answer for its own management name only on the management and setup networks. | DNS query from a guest client |
| ENK-NET-010 | The management network shall be broadcast under its name. It shall not be hidden. | Inspection |

#### Hardening

These apply to every release image.

| ID | Requirement | Verification |
|---|---|---|
| ENK-HARD-001 | No account shall allow login without a credential that was generated for, or chosen on, that device. | Inspection of the image; login attempts |
| ENK-HARD-002 | No remote shell shall be reachable on any network. | Port scan on every network |
| ENK-HARD-003 | Failsafe mode shall give no network access to the device. | Test: trigger failsafe, scan |
| ENK-HARD-004 | No general-purpose administration interface shall be installed. | Inspection of the package list |
| ENK-HARD-005 | The image shall contain no network service that section 3 does not list. | Comparison of listening sockets with section 3 |
| ENK-HARD-006 | The device shall report, for each of ENK-HARD-001 to 005, whether it is met. | Test on a modified device |
| ENK-HARD-007 | A development build may deviate from this section. It shall identify itself as a development build on every page of the management UI and shall not be published as a release. | Inspection |

### 5. What separation does not do

Enkrnett states these limits to the operator (ENK-SCOPE-004).

| Limit | Reason | Source |
|---|---|---|
| A guest can still send broadcast frames to other guests. | All clients of one BSS share a group key. | [AirSnitch][airsnitch] |
| Clients without OWE on a Transition Mode network are not encrypted. | By design of Transition Mode. | [Wi-Fi Alliance][wfa-guide] §2.11 |
| A fake access point with the same name is not prevented. | OWE has no authentication. | [RFC 8110][rfc8110] §7 |
| Traffic is protected on the radio link only. | Same. | [RFC 8110][rfc8110] §7 |
| Anyone who can touch the device can reset it. | Physical access. | RFC 004 |

The status shown to the operator says "blocked by this device" for what ENK-ISO requires and
lists these limits. It never says "isolated" or "secure" without qualification.

### 6. Hardware note

OpenWrt builds the MT7628 target without process jails and without position-independent
executables ([`target.mk`][mt76x8-target], [`include/target.mk`][target-mk]). On that target the
separation in this RFC rests on the firewall and the bridges alone. Device profiles state this
(RFC 005).

## Consequences

| Affected | Change |
|---|---|
| Draft requirement "dedicated AP topology" (bridge) | Replaced by ENK-TOPO-001. |
| Draft requirement "dedicated AP mode" as the way to save resources | Withdrawn. The default image shows that routing fits on 8 MB devices. |
| Draft future item "client isolation" | Becomes ENK-ISO-001 to 006, in the first release. |
| Draft status field `lan_isolation` | Replaced by the statuses of ENK-ISO and section 5. |
| Draft status field `upstream_security` | Withdrawn. It could only say "unknown". |
| Draft baseline "mDNS discovery" | Withdrawn. The management network resolves the device's name (RFC 003). |
| Guest IPv6 | Not offered in the first release. |

## Alternatives considered

| Alternative | Why not |
|---|---|
| Bridge access point; isolation by the site router | The operator cannot configure it. Contradicts the regulator's guidance. |
| Bridge access point with layer-2 filtering on the device | Not a standard OpenWrt arrangement; fragile; research shows such filters are often bypassed. |
| Management through the guest network with application-layer protection | Exposes the API to every guest and needs cryptography that a page served over HTTP cannot protect. |
| Management from the uplink side only | Fails where the device is the venue's only Wi-Fi. |
| Management network that appears only after a button press | Needs physical access for every status check. |
| Hidden management network | Phones then probe for it everywhere, and joining it is harder. |
| IPv6 for guests | Doubles the rule set and the test matrix for little benefit in a café. |

## Verification

| Step | Where |
|---|---|
| Every requirement above is tested from a real client on each network. | Tier 1 device |
| The same tests run against simulated radios. | Virtual machine (RFC 006, M-6) |
| Isolation of the automatically created open BSS in Transition Mode. | RFC 006, M-4 |
| Memory with routing, firewall, and DHCP on a 64 MB device. | RFC 006, M-3 |

## Open questions

| # | Question | Proposal |
|---|---|---|
| 1 | Is the bridge topology offered at all in the first release? | **No.** One topology means fewer states to explain and to test. A later RFC may add it for sites that already have a guest segment. |
| 2 | May the owner allow management from the uplink side? | **Not in the first release.** |
| 3 | May an expert enable a remote shell? | **Not through Enkrnett.** A device modified by other means reports ENK-HARD-002 as not met. |
